This is a DIFFERENT capture path from everything else in this module. Phases 1–4 all observe traffic live, through the storefront beacon and the module's own REST endpoint, and persist what they observe. This instead parses a raw web-server access log **after the fact, on demand, and keeps nothing** — no new database table, no cron, no retention policy. A run reads the referenced file, computes a report in memory, shows it on the page and offers a download, then keeps nothing beyond that one request/response. It is a SIMULATOR / offline analysis TOOL, not a second capture pipeline, and depends on none of Phases 1–4's tables.

**Resolved by the 2026-09-20 refinement:**
- **No persistence, anywhere.** No new `db_schema.xml` table, no report-history, no cron. This is the single biggest simplification to the original sketch: the whole feature is a stateless "point at a file → get numbers → optionally download them" utility, not a Magento entity with its own admin grid.
- **The log format is admin-described, not assumed.** Earlier drafts of this plan assumed a fixed Apache/Nginx "combined log format" and a regex parser for it. That assumption is dropped. Instead the admin describes the file's own shape before analysing it:
  - **Delimiter** — a single character the columns are split on. The user's own examples are space, comma and pipe; the field should accept any single character (or a short list of named presets — Space / Comma / Pipe / Tab — plus a free-text override), not a fixed enum of exactly three, since a real access log format the user has may differ.
  - **URL column** — which column (by position) holds the request URL.
  - **Status column** — which column (by position) holds the HTTP response status code ("the url status data").
  - This makes the parser a generic delimited-column reader, not a log-format-specific one: it works against any consistently-delimited log line, Apache/Nginx or otherwise, as long as the admin can say which column is which. Column positions are 1-indexed in the admin UI (matching how a human counts columns), converted to a 0-indexed array offset internally.

**Still open — needs the user's decision when implementation actually starts:**
- **What counts as "blocked"?** Now directly answerable from the admin-specified status column: the natural design is an admin-editable list of status codes (e.g. `403,429,503`) or ranges that count as "blocked" — matching this module's existing config-driven philosophy (CLAUDE.md #2) rather than a hardcoded set. Needs the user's confirmation, and specifically whether "blocked" should mean ONLY status code, or also match against a bot/UA pattern if the log format the user actually has includes a user-agent column.
- **What counts as "a purchase"?** The delimited format as described (delimiter + URL column + status column) has no order-success signal beyond the URL itself. The working assumption remains: an admin-configured URL pattern (e.g. a substring or simple wildcard match against `/checkout/onepage/success/`, adjustable since a custom checkout's success URL may differ) counts a matching, non-blocked request as a purchase. This is a proxy, not ground truth the way `sales_order` is, and should be labelled as such wherever it's displayed.
- **What counts as a "visitor"?** This is the one question the refinement did NOT resolve, and is now the most important remaining gap: the described format (delimiter, URL column, status column) does not mention a client-identifying column at all. Without an IP address or similar column, "how many visitors" cannot be computed as unique entities — only "how many qualifying requests" can be, which is a request count, not a visitor count. Before implementation starts, confirm with the user either (a) the real log format also has an IP/client-id column, and get its position too, so "visitors" can mean unique values in that column (optionally within a time window, to avoid one long-lived crawler being counted as thousands of "visitors"), or (b) the user is deliberately fine with "visitors" meaning "qualifying request count" as a simplification, which should be labelled clearly on the report rather than implied to be a true unique-visitor figure.
- **File input mechanism.** Still assumed to be a server-side path field ("read urls from file"), not a browser upload — meaning the file already exists on, or is reachable by, the app server's filesystem. This has its own security surface (path traversal, arbitrary file read via a crafted path) that needs deliberate handling — likely restricting the path to a configured base directory, the same "never trust a string into a path" principle already applied elsewhere in this module (`AdSpendCsvFile::pathFor()`, `EventValidator`'s click-id allow-list) — rather than accepting any absolute path a form field is given.
- **Archive support.** "Compressed (tar, zip, etc.)" still needs a concrete supported-format list — `.tar`, `.tar.gz`/`.tgz`, `.zip`, and plain `.log`/`.txt` are the obvious set — and, since nothing is persisted, decompression can now be a pure streaming read (decompress and process one line at a time, discard as it goes) rather than extracting to a temp file first, which simplifies the earlier "large archive" memory concern considerably.
- **Download format.** Presumably CSV (a handful of summary numbers, not a table worth a PDF), matching the general shape of what P4-T1 already established for the rest of the module, but not yet confirmed.
- **Quoted/escaped fields.** A comma- or pipe-delimited log that also quotes fields containing the delimiter (CSV-style) needs a decision on whether to support quote-aware splitting or require the admin to pick a delimiter that does not collide with the data.
